# Master Knowledge Document: Kubernetes PVC & Volume Re-Binding (CKA Scenario)

---

## 1. Executive Summary

This document details the resolution of a Certified Kubernetes Administrator (CKA) exam scenario where a stateful MariaDB deployment is deleted while its underlying Persistent Volume (PV) survives due to a `Retain` reclaim policy. The objective is to construct a Persistent Volume Claim (PVC) matching the exact storage attributes of the orphaned PV ($250\text{Mi}$ capacity, `ReadWriteOnce` access mode, target namespace `mariadb`), bind them, and update the restored Deployment manifest to mount the volume at `/var/lib/mysql`. Executing this process requires verifying the PVC state transitions from `Pending` to `Bound` before triggering deployment rollouts, guaranteeing zero data loss during stateful application recovery.

---

## 2. Key Takeaways

* **Data Retention Strategy**: A PV configured with `persistentVolumeReclaimPolicy: Retain` preserves data and underlying storage assets even if the bound PVC or Deployment is deleted.
* **Exact Spec Matching**: To bind an unassigned PV without dynamic provisioning, the PVC spec must match or fall within the PV's capacity ($C_{\text{PV}} \ge C_{\text{PVC}}$), access modes, and storage class attributes.
* **Static Volume Binding**: Specifying `spec.volumeName` in a PVC manifest explicitly binds it to a specific PV, bypassing default dynamic provisioner selection algorithms.
* **Verification Prerequisite**: Updating a Deployment to reference an unbound (`Pending`) PVC causes pods to get stuck in `ContainerCreating` or `CreateContainerError` states. PVC binding status must always be verified prior to workload application.
* **Declarative Consistency**: Deployment pods access claims via a two-tier linkage: `spec.template.spec.volumes[].persistentVolumeClaim.claimName` matches the PVC name, and `spec.template.spec.containers[].volumeMounts[].name` matches the internal volume handle.

## 4. Beginner Explanation (ELI5)

Imagine you rent a **storage locker** (Persistent Volume or **PV**) to hold a box of important toys (your database data). You are handed a **claim ticket** (Persistent Volume Claim or **PVC**) that proves Locker #5 belongs to you. 

One day, someone accidentally throws away your claim ticket and your worker instructions (the **Deployment**). However, the rental facility has a **"Retain" policy**, meaning they will **not** throw away the contents of Locker #5 just because the ticket disappeared.

To fix this:
1. You fill out a **new claim ticket** (a new PVC) requesting a locker with at least $250\text{Mi}$ of space and standard single-person access (`ReadWriteOnce`). You explicitly write "Locker #5" on the ticket.
2. The facility matches your ticket to Locker #5. The status turns to **Bound** (meaning the key works!).
3. You hire a **new worker** (Deployment) and give them instructions: *"Go to Locker #5 using this claim ticket, open it, and place the toy box onto the shelf inside your room (`/var/lib/mysql`)."*

## 5. Technical Deep Dive

### Storage Controller Binding Logic Architecture

The Kubernetes Control Plane runs the `persistentvolume-controller`, an asynchronous control loop that evaluates unassigned PVCs against available PVs.

```
   +-----------------------+              +-----------------------+
   | PersistentVolumeClaim |              |    PersistentVolume   |
   |     (Namespace: A)    |              |   (Cluster-Scoped)    |
   +-----------------------+              +-----------------------+
   | Name: mariadb         |              | Name: pv-mariadb-01   |
   | Request: 250Mi        |  Match Logic | Capacity: 250Mi       |
   | Access: ReadWriteOnce |------------->| Access: ReadWriteOnce |
   | ClaimName: mariadb    |   Evaluates  | Reclaim: Retain       |
   +-----------------------+              +-----------------------+
               |                                      |
               +------------------+-------------------+
                                  |
                                  v
                        +-------------------+
                        |   Status: BOUND   |
                        +-------------------+
```

#### Binding Phase Criteria Evaluation

For a PVC to successfully bind to a PV without dynamic storage class involvement, the controller checks four constraints:

1. **Storage Class Matching**: 
   $$\text{StorageClass}(\text{PVC}) == \text{StorageClass}(\text{PV})$$
   *(If unset or set to `""`, both must match as empty).*

2. **Access Mode Subset**:
   $$\text{AccessModes}(\text{PVC}) \subseteq \text{AccessModes}(\text{PV})$$

3. **Capacity Threshold**:
   The volume's physical capacity ($C_{\text{PV}}$) must meet or exceed the claim's requested capacity ($C_{\text{PVC}}$):
   $$C_{\text{PV}} \ge C_{\text{PVC}}$$

4. **Explicit Direct Binding (Optional)**:
   If `spec.volumeName` is provided, the controller skips general binding algorithms and binds directly to the targeted PV, provided the capacity and access mode criteria are met.

### Storage Capacity & Resource Allocation Metrics

When planning capacity allocations for stateful pod deployments across a cluster with $N$ replica pods, resource requests are calculated as follows:

#### Aggregate PVC Capacity Requirement
$$\text{Total Storage Requirement} = \sum_{i=1}^{N} C_{\text{PVC}_i}$$

#### Node Resource Allocation Sizing Logic
When scheduling a pod that mounts a PVC, the kube-scheduler must ensure the target Node ($N_{\text{target}}$) has sufficient resource headroom for container requests alongside storage execution overhead:

$$\text{Allocatable Memory}_{N} \ge \sum_{j=1}^{M} \text{Memory Request}_{\text{Pod}_j} + \text{System Reserved}$$

$$\text{Allocatable CPU}_{N} \ge \sum_{j=1}^{M} \text{CPU Request}_{\text{Pod}_j} + \text{System Reserved}$$

### State Machine of Persistent Volumes

```
 [ Available ] ---> (PVC Created & Matched) ---> [ Bound ]
       ^                                             |
       |                                      (PVC Deleted)
       |                                             |
  (Reclaimed)                                        v
 [ Released ] <--- (Retain Policy Holds Data) <------+
```

* **Available**: Volume is free to be bound.
* **Bound**: Volume is reserved exclusively by a single PVC.
* **Released**: PVC has been deleted, but physical storage resource remains un-cleared under `Retain` policy.
* **Failed**: Automated reclamation or binding failure state.

## 6. Important Definitions

* **PersistentVolume (PV)**: A cluster-scoped storage resource provisioned by an administrator or dynamically through StorageClasses.
* **PersistentVolumeClaim (PVC)**: A namespace-scoped request for storage by a user, specifying size, access modes, and optional binding constraints.
* **Reclaim Policy**: The policy instructing Kubernetes on handling a PV when its claim is released (`Retain`, `Delete`, or `Recycle`).
* **ReadWriteOnce (RWO)**: An access mode allowing the volume to be mounted as read-write by a single node at a time.
* **StorageClass**: A resource object defining provisioners and parameters for dynamic volume provisioning.

## 7. Code Snippets & Configuration Examples

### PVC Manifest Definition (`mariadb-pvc.yaml`)

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mariadb
  namespace: mariadb
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 250Mi
  # Ensures manual binding to an existing PV with no storage class defined
  storageClassName: ""
  # Uncomment to explicitly bind to a named PV if auto-matching is disabled
  # volumeName: pv-mariadb-01
```

### Complete Deployment Integration (`MARB_deployment.yaml`)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mariadb-deployment
  namespace: mariadb
  labels:
    app: mariadb
spec:
  replicas: 1
  selector:
    matchLabels:
      app: mariadb
  template:
    metadata:
      labels:
        app: mariadb
    spec:
      containers:
      - name: mariadb-container
        image: mariadb:10.5
        env:
        - name: MYSQL_ROOT_PASSWORD
          value: "SecretPassword123"
        ports:
        - containerPort: 3306
          name: mysql
        volumeMounts:
        - name: mariadb-persistent-storage
          mountPath: /var/lib/mysql
      volumes:
      - name: mariadb-persistent-storage
        persistentVolumeClaim:
          claimName: mariadb
```

### CLI Verification Workflow Execution

```bash
# 1. Apply the PVC manifest in the target namespace
kubectl apply -f mariadb-pvc.yaml

# 2. Verify that the PVC transitions to the 'Bound' status
kubectl get pvc mariadb -n mariadb

# Expected Output:
# NAME      STATUS   VOLUME          CAPACITY   ACCESS MODES   STORAGECLASS   AGE
# mariadb   Bound    pv-mariadb-01   250Mi      RWO                           10s

# 3. Apply or update the Deployment manifest
kubectl apply -f MARB_deployment.yaml

# 4. Verify pod deployment rollout and container initialization status
kubectl get pods -n mariadb -l app=mariadb

# 5. Inspect deep events if the pod is stuck in pending state
kubectl describe pod -n mariadb -l app=mariadb
```

## 8. Best Practices

* **Always Verify PVC State Before Deployment**: Ensure the PVC status reads `Bound` before applying workload configurations to prevent scheduling bottlenecks.
* **Explicit StorageClass Declaration**: When targeting existing static PVs without dynamic provisioners, explicitly set `storageClassName: ""` in the PVC manifest.
* **Namespace Alignment**: Ensure the PVC resides in the exact namespace as the target Deployment; PVCs cannot cross namespace boundaries.
* **Decouple Data Lifecycles**: Always use `Retain` reclaim policies for production stateful workloads (databases, message queues) to prevent accidental data deletion during namespace or deployment teardowns.
* **Match Indentation Strictly**: Ensure `volumes` exists under `spec.template.spec` and `volumeMounts` exists under `spec.template.spec.containers[]`.

## 9. Common Mistakes

| Mistake | Root Cause | Symptom | Remediation |
| :--- | :--- | :--- | :--- |
| **PVC stuck in `Pending`** | Request size $C_{\text{PVC}} > C_{\text{PV}}$ or mismatched StorageClass | PVC status shows `Pending` indefinitely | Lower requested size to match PV or clear `storageClassName`. |
| **Namespace Mismatch** | PVC created in `default` instead of `mariadb` | Deployment Pod fails: `claim "mariadb" not found` | Add `-n mariadb` to `kubectl apply` or specify `metadata.namespace`. |
| **Mismatched Volume Handles** | `volumeMounts[].name` does not match `volumes[].name` | YAML Validation Error / Deployment creation fails | Standardize internal volume label across container and pod specs. |
| **Mounted on Wrong Path** | Incorrect `mountPath` configured | Database initializes fresh empty dir, ignoring old data | Set `mountPath` explicitly to database data path (`/var/lib/mysql`). |

## 10. Real-World Examples

### Case 1: Recovery from Accidental Deployment Deletion
An SRE accidentally deletes a namespace's helm release containing a MySQL cluster. Because the underlying storage provisioner created PVs backed by external SAN volumes with a `Retain` policy, re-applying the static PVC and Deployment specs immediately re-binds the existing volumes, fully restoring operations without data restoration from backups.

### Case 2: Zero-Downtime Storage Schema Upgrades
A stateful service needs to migrate from an unmanaged standalone pod to an orchestrated deployment. Engineers define a PVC matching the existing persistent storage handle, verify `Bound` status, and seamlessly attach the existing data directory to the new deployment structure.
