## 1. Executive Summary

This guide provides a technical analysis of diagnosing and restoring a broken Kubernetes cluster following a host migration, specifically tailored for the Certified Kubernetes Administrator (CKA) exam. When a `kubeadm`-provisioned node is migrated to a new machine or IP address, control plane services frequently fail due to outdated static pod configurations and network endpoint mismatches. 

The primary symptom is API server unreachability ("connection refused"). Systematic diagnosis using low-level container host tools (`crictl`, `journalctl`, `curl`) reveals root causes such as misconfigured `--etcd-servers` parameters in the `kube-apiserver` manifest and unschedulable static pods caused by excessive CPU resource requests in `kube-scheduler.yaml`. By updating static pod manifests in `/etc/kubernetes/manifests/`, administrators leverage the kubelet's file-watching mechanism to automatically recreate control plane components, restoring full cluster availability.

---

## 2. Key Takeaways

* **Decoupled Diagnostics**: When the API server is unreachable, standard `kubectl` commands fail; diagnostic procedures must pivot to host-level utilities like `crictl`, `journalctl`, and direct file system inspection.
* **Etcd Endpoint Alignment**: The `kube-apiserver` relies directly on `etcd`. Misaligned IP addresses or ports in the `--etcd-servers` flag cause `kube-apiserver` to enter a `CrashLoopBackOff` loop.
* **Static Pod Lifecycle**: Kubelet continuously watches `/etc/kubernetes/manifests/`. Any modifications to manifest files automatically trigger kubelet to stop, recreate, and restart the target pod containers.
* **Resource Request Deadlocks**: Excessive resource requests (`resources.requests.cpu`) in static pod manifests prevent pods from transitioning from `Pending` to `Running` if the requested millicores exceed node allocatable capacity.
* **Targeted Health Checks**: Direct health checks using `curl` against local or external etcd endpoints (`https://127.0.0.1:2379/health`) validate underlying storage availability prior to modifying API server manifests.

## 3. Topics Covered

* **Control Plane Diagnostic Bootstrapping**: Transitioning from broken `kubectl` client interactions to host-level log and container inspection using `crictl` and `systemctl`.
* **Etcd Connectivity & API Server Recovery**: Identifying `CrashLoopBackOff` causes in `kube-apiserver` and updating `--etcd-servers` bindings to match active network interfaces or localhost.

* **Post-Migration Verification Procedures**: Executing systematic node state and system-wide pod health checks to guarantee complete cluster recovery.

## 4. Technical Deep Dive

### Control Plane Architecture & Node Migration Failure Dynamics

In a standard `kubeadm` single-node or multi-master setup, control plane components (`kube-apiserver`, `etcd`, `kube-scheduler`, `kube-controller-manager`) run as **Static Pods**. These pods are managed directly by the local `kubelet` daemon rather than through the `kube-apiserver` control loop.

```
                    +-------------------------------------------------+
                    |                   Kubelet Daemon                |
                    |   (Watches /etc/kubernetes/manifests/*.yaml)    |
                    +------------------------+------------------------+
                                             |
                                     Recreates Pods
                                             |
                                             v
+-----------------------------------------------------------------------------------+
| Container Runtime (Containerd / CRI-O via crictl)                                 |
|                                                                                   |
|  +--------------------+      gRPC / HTTP      +--------------------------------+  |
|  |   kube-apiserver   | --------------------> |              etcd              |  |
|  | (CrashLoopBackOff) | <-------------------  |  (127.0.0.1:2379 / Health)     |  |
|  +--------------------+      Endpoint Error   +--------------------------------+  |
|            ^                                                                      |
|            | Resource Request Evaluation                                          |
|  +--------------------+                                                           |
|  |   kube-scheduler   |                                                           |
|  |     (Pending)      |                                                           |
|  +--------------------+                                                           |
+-----------------------------------------------------------------------------------+
```

When a node machine is migrated, its network interfaces, local IP bindings, or host system hardware configurations often change. This causes two cascading failure modes:

#### 1. API Server to Etcd Endpoint Mismatch
The `kube-apiserver` binary takes an explicit command-line flag `--etcd-servers`. If this flag references a stale host IP address (e.g., `https://192.168.1.50:2379`) instead of loopback (`https://127.0.0.1:2379`) or the updated node IP, TCP connection establishment fails. The `kube-apiserver` container logs present repeated write errors and connection refusals, forcing the runtime into a `CrashLoopBackOff` state.

#### 2. Kubelet Resource Allocation & Predicate Evaluation Failure
Node capacity dictates whether a pod can be scheduled or run. Kubelet calculates Node Allocatable capacity using the following relationship:

$$\text{Capacity}_{\text{allocatable}} = \text{Capacity}_{\text{total}} - \text{Reserved}_{\text{kube-reserved}} - \text{Reserved}_{\text{system-reserved}} - \text{Threshold}_{\text{eviction}}$$

Where:
* $\text{Capacity}_{\text{total}}$: The total physical hardware resources (CPU, Memory) detected by the kernel.
* $\text{Reserved}_{\text{kube-reserved}}$: Resources explicitly set aside for Kubernetes system daemons (`kubelet`, `containerd`).
* $\text{Reserved}_{\text{system-reserved}}$: Resources reserved for OS system processes (`systemd`, `sshd`).
* $\text{Threshold}_{\text{eviction}}$: Memory/disk capacity buffer reserved to prevent host OOM (Out Of Memory) conditions.

For a static pod $P_{\text{static}}$ requesting CPU millicores $R_{\text{cpu}}$, the pod scheduling or runtime binding predicate requires that:

$$\sum_{i=1}^{K} R_{i, \text{cpu}} + R_{\text{static}, \text{cpu}} \le \text{Capacity}_{\text{allocatable}, \text{cpu}}$$

Where $K$ represents the total count of currently running containers on the node.

If a migrated manifest specifies an unrealistic CPU request—such as $R_{\text{scheduler}, \text{cpu}} = 4000\text{m}$ ($4\text{ CPU cores}$) on a system where $\text{Capacity}_{\text{allocatable}, \text{cpu}} = 2000\text{m}$ ($2\text{ CPU cores}$)—the allocation inequality fails:

$$4000\text{m} > 2000\text{m} \quad \implies \quad \text{Scheduling Predicate Failure}$$

Consequently, the pod remains stuck in a `Pending` state or is rejected by the kubelet runtime manager.

## 5. Important Definitions

* **Static Pod**: A pod managed directly by the `kubelet` daemon on a specific node, bypassing the Kubernetes API server, with manifest files located in `/etc/kubernetes/manifests`.
* **crictl**: A CLI tool for Container Runtime Interface (CRI)-compatible container runtimes, used to inspect low-level pods, containers, and logs when `kubectl` is unavailable.
* **CrashLoopBackOff**: A Pod status indicating that a container in the pod repeatedly crashes, wakes up, and crashes again, triggering exponential backoff delays by the runtime.
* **Etcd**: A strongly consistent, distributed key-value store used as Kubernetes' backing store for all cluster state and metadata.
* **Kubelet**: The primary node-level agent that reads pod specifications and ensures that containers described in those specifications are running and healthy.

## 6. Code Snippets & Configuration Examples

### Step 1: Diagnose Control Plane Failures Host-Side

When `kubectl` yields `The connection to the server was refused`, run CRI runtime diagnostics on the node:

```bash
# List all running and stopped control plane containers via crictl
sudo crictl ps -a

# Inspect logs of the failing kube-apiserver container
sudo crictl logs $(sudo crictl ps --name kube-apiserver -q)

# Alternatively, inspect kubelet service logs via journalctl
sudo journalctl -u kubelet -f --no-pager
```

### Step 2: Validate Etcd Endpoint Health Direct via Curl

Verify whether `etcd` is active locally on port `2379`:

```bash
# Test local etcd health endpoint over HTTPS bypassing TLS verification
curl -k https://127.0.0.1:2379/health

# Expected Output:
# {"health":"true"}
```

### Step 3: Patch `kube-apiserver.yaml` Manifest

Edit `/etc/kubernetes/manifests/kube-apiserver.yaml` to fix the `--etcd-servers` IP address binding:

```yaml
apiVersion: v1
kind: Pod
metadata:
  annotations:
    kubeadm.kubernetes.io/kube-apiserver.advertise-address.option: ""
  creationTimestamp: null
  labels:
    component: kube-apiserver
    tier: control-plane
  name: kube-apiserver
  namespace: kube-system
spec:
  containers:
  - command:
    - kube-apiserver
    - --advertise-address=192.168.1.100
    - --allow-privileged=true
    # CORRECTED ETCD ENDPOINT: Change outdated external IP to localhost or valid interface
    - --etcd-servers=https://127.0.0.1:2379
    - --client-ca-file=/etc/kubernetes/pki/ca.crt
    - --etcd-cafile=/etc/kubernetes/pki/etcd/ca.crt
    - --etcd-certfile=/etc/kubernetes/pki/apiserver-etcd-client.crt
    - --etcd-keyfile=/etc/kubernetes/pki/apiserver-etcd-client.key
    image: registry.k8s.io/kube-apiserver:v1.28.0
    name: kube-apiserver
```

### Step 4: Patch `kube-scheduler.yaml` Oversized Resource Requests

Edit `/etc/kubernetes/manifests/kube-scheduler.yaml` to ensure resource requests fit within node allocatable limits:

```yaml
apiVersion: v1
kind: Pod
metadata:
  labels:
    component: kube-scheduler
    tier: control-plane
  name: kube-scheduler
  namespace: kube-system
spec:
  containers:
  - command:
    - kube-scheduler
    - --authentication-kubeconfig=/etc/kubernetes/scheduler.conf
    - --authorization-kubeconfig=/etc/kubernetes/scheduler.conf
    - --bind-address=127.0.0.1
    - --kubeconfig=/etc/kubernetes/scheduler.conf
    - --leader-elect=true
    image: registry.k8s.io/kube-scheduler:v1.28.0
    name: kube-scheduler
    resources:
      requests:
        # REDUCED CPU REQUEST: Reduced from 4 (4000m) to 100m to fit allocatable capacity
        cpu: 100m
        memory: 128Mi
```

### Step 5: Post-Fix Cluster Verification

Once changes are saved, kubelet auto-recreates the pods. Verify cluster state via `kubectl`:

```bash
# Check control plane and cluster node status
kubectl get nodes -o wide

# Check health of all system pods across namespaces
kubectl get pods -n kube-system

# Verify core cluster control plane components health
kubectl get componentstatuses # Note: Deprecated in newer versions, use pod health
```

## 7. Best Practices

* **Use Loopback for Co-located Control Plane Services**: Point `--etcd-servers` in `kube-apiserver.yaml` to `https://127.0.0.1:2379` when `etcd` runs co-located on the same host, avoiding external IP dependency failures during network migrations.
* **Preserve Static Pod Manifest Backups**: Before editing any manifest in `/etc/kubernetes/manifests/`, copy the original file to a temporary directory outside the watch path (e.g., `cp /etc/kubernetes/manifests/kube-apiserver.yaml /tmp/`).
* **Set Minimal Resource Requests on Static Pods**: Keep CPU and memory requests for core control plane static pods as small as practical to prevent scheduling deadlocks on low-resource or single-node environments.
* **Utilize Host Diagnostics First**: When API endpoints refuse connections, immediately switch diagnostic context to host utilities (`crictl`, `journalctl`, `systemctl status kubelet`) rather than repeatedly running `kubectl`.

---

## 8. Common Mistakes

* **Editing Files directly inside Non-Watched Directories**: Modifying copies of manifests in temporary locations and expecting changes to apply without moving them into `/etc/kubernetes/manifests/`.
* **Placing Temporary Manifest Backups in `/etc/kubernetes/manifests/`**: Kubelet attempts to instantiate **every** valid YAML file in that folder. Placing `kube-apiserver.yaml.bak` inside `/etc/kubernetes/manifests/` causes duplicate container name conflicts.
* **Confusing Etcd Client and Peer Ports**: Configuring `kube-apiserver` to talk to etcd's peer port (`2380`) instead of its client port (`2379`).
* **Over-specifying Limits and Requests**: Setting static pod CPU requests in terms of full cores (e.g., `cpu: 4`) without verifying node capacity via `lscpu` or `kubectl describe node`.

## 9. Real-World Examples

### Bare-Metal to Cloud VM Node Migration
An enterprise migrates a single-node staging cluster from an on-premises Bare-Metal server ($32\text{ cores}, 128\text{ GB RAM}$) to a smaller cloud virtual machine instance ($2\text{ vCPUs}, 8\text{ GB RAM}$).

#### System Failure
* The network interface IP changes from `10.0.1.50` to `172.16.0.12`.
* `kube-apiserver` crashes because `--etcd-servers` hardcodes `10.0.1.50:2379`.
* Once `kube-apiserver` is pointed to `127.0.0.1:2379`, `kube-scheduler` remains stuck in `Pending` because its manifest required `cpu: 4`, which exceeds the virtual machine's available $2\text{ vCPUs}$.

#### Remediation Sequence
1. The platform engineer logs into the host via SSH.
2. Uses `sudo crictl logs` to discover the `etcd` TCP dial failure in `kube-apiserver`.
3. Edits `/etc/kubernetes/manifests/kube-apiserver.yaml`, updating the `--etcd-servers` flag to `https://127.0.0.1:2379`.
4. Observes `kubectl get pods -A` showing `kube-scheduler` as `Pending`.
5. Edits `/etc/kubernetes/manifests/kube-scheduler.yaml` to change `cpu: 4` to `cpu: 100m`.
6. Re-checks cluster state; all control plane pods transition to `Running`.

## 10. Glossary

* **API Server (`kube-apiserver`)**: The primary control plane component exposing the Kubernetes API; validates and configures data for API objects.
* **CRI (Container Runtime Interface)**: A plugin interface enabling Kubelet to use a wide variety of container runtimes (such as containerd or CRI-O) without needing to recompile.
* **Etcd Client Port (`2379`)**: The network port used by clients (such as `kube-apiserver`) to communicate with the `etcd` key-value store.
* **Etcd Peer Port (`2380`)**: The network port used for inter-node communication between `etcd` cluster members.
* **Kubelet Manifest Directory**: The node host directory (default: `/etc/kubernetes/manifests`) monitored by Kubelet to run static pods.
* **Node Allocatable**: The actual available resources on a node designated for pods, excluding system and Kubernetes reserved overhead.
